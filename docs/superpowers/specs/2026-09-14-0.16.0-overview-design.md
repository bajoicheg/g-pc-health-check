# 0.16.0 — Bilingual Service Desk actions and one-click repair

## Intent

0.16.0 turns the current diagnostic-focused single EXE into a more complete Service Desk workstation tool while preserving the security boundaries already proven in 0.15.x. The release combines four approved product changes:

1. a bilingual RU/EN user interface with persistent in-app switching;
2. faster operator workflows (human-readable MB sizes, auto-collection where safe, Select All, About, corrected branding);
3. a centralized Service Desk action registry and two explicit batch buttons — **Сделать хорошо / Make it better** and **Сделать всё / Do everything**;
4. a broadened, fixed allow-list of workstation remediation actions, including intentionally disruptive network/printing/policy/service repairs, with one confirmation and one UAC elevation for the administrative portion.

The owner explicitly approved this broadened remediation scope for 0.16.0. The only absolute product exclusion requested for the red batch is disabling or weakening protective software. This specification adds further evidence-preservation boundaries that do not conflict with that request: no forced reboot/logoff, no Event Log clearing, no profile/credential deletion, and no arbitrary command execution.

## Component specifications

This release is deliberately decomposed so each subsystem can be reasoned about and tested independently while still shipping as one 0.16.0 candidate:

- `2026-09-14-0.16.0-ui-localization-design.md` — MB presentation, analysis auto-collection, RU/EN, About, flags and shield background.
- `2026-09-14-0.16.0-action-model-design.md` — action registry, recommendation semantics, Select All, green/red button UX and preflight.
- `2026-09-14-0.16.0-remediation-design.md` — exact remediation allow-list, execution hosts, ordering, UAC orchestration, impact and negative security boundaries.

The implementation plan must cover all three specs. The implementation may be task-phased, but partial functionality is not a 0.16.0 release.

## Release architecture

Keep one portable Windows x64 EXE. Do not add a service, driver, installer, background agent, remote controller, cloud dependency or arbitrary script engine.

The release uses three clear layers:

- **Presentation/localization** — UI text, culture selection, About, size formatting and safe auto-start behavior.
- **Action model/orchestration** — stable action IDs and metadata, dynamic availability, batch preflight, confirmation, selection semantics and result aggregation.
- **Execution** — the existing current-process/elevated-worker boundary, extended with only fixed action handlers. The worker remains authenticated by the existing session/nonce model and accepts no free-form command, path, service name, adapter name or script from the UI.

The existing diagnostic collectors, score/coverage meaning, read-only evidence windows and report models remain separate from remediation. Missing telemetry stays unknown/partial, never healthy by implication.

## Main-window operator flow

The recommendations area keeps its existing checkboxes and **Применить выбранное / Apply selected** workflow. Add:

- **Выбрать все доступные / Select all available** — selects every current recommendation that is automated and dynamically requestable. Manual rows and unavailable rows remain unselected/read-only.
- green **Сделать хорошо / Make it better** — uses only current actions classified as Recommended, automated and dynamically available;
- red **Сделать всё / Do everything** — requests the entire 0.16.0 `IncludeInDoEverything` registry set, independent of whether the current scan recommends each action.

Neither batch button starts work before its confirmation dialog is accepted.

### Green button

The green dialog shows:
- exact actions that will run;
- actions that were recommended but cannot run, with reasons;
- highest risk in the batch;
- affected scopes;
- whether UAC is required;
- an explicit statement that diagnostics will run again afterwards.

If no recommended automated action is requestable, the button is disabled or produces a non-modifying explanation. It must not run Optional actions merely to make the batch non-empty.

### Red button

The red dialog is intentionally stronger. It shows the full requested action list and a concise impact summary stating that the batch can:
- interrupt network access, VPN and an RDP session;
- release/renew DHCP leases and reset network stacks;
- restart connected physical network adapters;
- remove pending print jobs;
- restart selected Windows services;
- force Group Policy refresh;
- require a later reboot for some changes;
- take a long time because DISM/SFC are included.

The confirmation also shows unavailable/skipped actions before execution. The operator accepts once; there is no per-action warning after that. UAC is requested once for the administrative portion when elevation is required.

## Security invariants carried forward

The following 0.15.x invariants are mandatory:

- portable EXE must work from any valid path and filename;
- UAC is explicit; the normal diagnostics process is not silently elevated;
- worker allow-list is fixed in code;
- nonce/session binding and named-pipe result validation remain mandatory;
- unknown/mixed worker actions remain rejected;
- elevated read-only Temp preview remains allowed;
- actual Temp deletion remains same-user, same-session, non-elevated parent behavior and never becomes an elevated-worker operation;
- no diagnostic collector interprets missing data as zero/healthy;
- no broad system-handle enumeration, raw/full SMART, treemap or stress/stability workloads are added by this release.

Additional 0.16.0 invariants:

- no action disables, stops, uninstalls, excludes, reconfigures or weakens antivirus, EDR, Windows Defender, firewall or other security controls;
- no generic service-control, registry-edit, PowerShell, CMD or arbitrary executable interface is exposed to the GUI or worker protocol;
- no forced reboot or forced logoff;
- no Event Log clearing;
- no deletion of browser data, credentials, user profiles or arbitrary user folders;
- every mutating action has a stable action ID, fixed implementation and evidence result;
- the red button may be disruptive, but it must be predictable and preflighted rather than free-form.

## Localization policy

Russian remains the default when no valid preference exists. English is a full supported UI language, not only translated menu names.

Language choice affects:
- main window;
- menus and dialogs;
- analysis-window controls/status text;
- remediation titles, reasons, risks and confirmations;
- generated human-readable HTML/clipboard summaries;
- About text and operator-facing errors.

Stable evidence identifiers, JSON property names, action IDs, schema values and exit/result codes do not change with language. Raw Windows/provider strings remain raw evidence and are not machine-translated.

## Evidence and result semantics

Every action result keeps:
- stable action ID;
- requested/runnable/executed/skipped state;
- start/finish timestamps where applicable;
- actual execution context and target scope;
- exit/result code when meaningful;
- bounded diagnostic message;
- whether reboot/reconnect/manual verification is required.

`Skipped` is not success. A red batch can finish `Partial` when an action is unavailable or fails while other actions succeed. The UI must not claim “everything fixed” merely because commands returned zero.

After green/red execution, run the existing post-remediation diagnostic flow in the original GUI process and present before/after evidence. Loss of RDP/VPN may prevent the operator from immediately seeing the GUI; that impact is a declared red-button risk, not hidden behavior.

## Version and release policy

Do not publish intermediate 0.16.0 assets from a test-only RED checkpoint. Version metadata and release notes are finalized only on the final release candidate after all functional tasks are GREEN.

Final target:
- Product/Assembly/File version: `0.16.0` / `0.16.0.0` as used by the existing project convention;
- fresh-main Windows build;
- published single-file EXE self-test;
- portable/security matrix;
- analyzer and supply-chain checks;
- exact-main GitHub Release `v0.16.0`;
- checksum, SPDX SBOM and provenance attestations;
- downloaded release bytes verified before an EXE link is given to the owner.

## Test-first policy

Each implementation task follows RED → GREEN. Connector-only development uses existing Windows CI for runtime evidence. Real destructive remediation is never executed in hosted CI; command/service/network handlers use synthetic/fake executor boundaries and negative worker tests. Existing safe self-tests and the portable matrix remain mandatory.

The final 0.16.0 candidate additionally requires managed Windows 11 pilot acceptance for:
- RU/EN switching and persistence;
- DPI 100/150/200 and resize repainting;
- ordinary admin-member, standard-user/alternate-admin UAC and already-elevated contexts;
- local console and RDP;
- VPN + EDR workstation;
- green batch on a machine with real recommended actions;
- red batch only on a disposable/approved pilot workstation because it is intentionally disruptive.

## Success criteria

0.16.0 is successful when a Service Desk engineer can understand the tool in Russian or English, open routine analysis views with minimal extra clicks, read file/folder sizes in MB, select all available recommendations, use a conservative green repair batch, deliberately use a fully preflighted red repair batch when appropriate, and obtain before/after evidence — without weakening security software, worker authentication, portable execution, Temp safety or diagnostic truthfulness.
