# 0.17.0 — Firmware and storage security posture

This component specification extends `2026-09-14-0.17.0-security-posture-design.md`. It is part of the same 0.17.0 release and implementation plan. Its firmware/storage requirements remain authoritative. The later `2026-09-14-0.17.0-local-admin-policy-design.md` supersedes only this file's weighted-control table by adding `SEC-LOCAL-ADMINS` and rebalancing the complete posture model back to exactly 100 points.

## Intent

Add three owner-requested security checks to Endpoint Security Posture v1:

1. presence of a BIOS/UEFI administrative configuration password;
2. firmware boot restrictions that prevent booting from anything except the approved internal Windows OS boot path;
3. encryption of all applicable fixed internal volumes, not only the Windows system volume.

All three checks are read-only in 0.17.0. The blue `Усилить защиту / Harden security` batch does not set firmware passwords, modify boot order, enable BitLocker, manipulate recovery protectors or store firmware credentials.

## Important terminology: “only C:”

Firmware does not know Windows drive letters such as `C:`. Therefore the product requirement is represented as:

> The normal and, where the vendor exposes it, alternate firmware boot configuration permits only the Windows Boot Manager / internal OS boot path associated with the currently running Windows system disk. External/removable/network/optical boot paths must be disabled or inactive.

The collector first identifies the Windows system volume and its underlying physical/internal disk. Firmware evidence is then correlated to Windows Boot Manager/internal storage rather than comparing firmware strings to the literal text `C:`.

Windows Recovery Environment reached through Windows Boot Manager remains allowed. A separate USB/PXE/DVD/SD/UEFI-shell boot entry is not considered the system `C:` path.

## Weighted baseline note

The firmware/storage controls retain these semantic weights in the final model unless superseded explicitly by the later local-admin component:

- `SEC-BITLOCKER-OS` — 8;
- `SEC-BITLOCKER-DATA` — 5;
- `SEC-SECUREBOOT` — 6;
- `SEC-BIOS-ADMIN-PASSWORD` — 5;
- `SEC-BOOT-RESTRICTIONS` — 4 in the final 0.17.0 allocation.

The authoritative complete 100-point table is in `2026-09-14-0.17.0-local-admin-policy-design.md`.

The existing score/coverage rules remain unchanged: `Unknown` lowers coverage but is not scored as failure; `Pass/Warn/Fail` are known; `NotApplicable` is used only when non-applicability is positively proven.

## `SEC-BIOS-ADMIN-PASSWORD`

### Security intent

Require a firmware password that protects changing BIOS/UEFI configuration. Vendor terminology differs:

- Lenovo: **Supervisor Password (SVP)**;
- Dell: **Admin / Setup password**;
- HP: **BIOS Setup / Administrator password**;
- other OEMs: equivalent configuration-protection password when a trustworthy read-only interface exists.

A Power-On Password is not a substitute for this control. A drive/HDD password is also not a substitute for BitLocker and is not required by the v1 baseline.

### Evaluation

- `Pass` — a trusted vendor interface positively reports that the administrative setup/supervisor password is set;
- `Fail` — a trusted vendor interface positively reports that no administrative setup/supervisor password is set;
- `Unknown` — vendor/interface unsupported, inaccessible, ambiguous or returns an unrecognized state.

Power-on/system-user/HDD password presence is retained only as supplemental evidence.

### Vendor adapters

Use separate read-only vendor adapters rather than parsing one universal BIOS string:

- Lenovo: query `Lenovo_BiosPasswordSettings` in `root\wmi`; interpret only documented password-state bits. Never request or submit a password for read-only collection.
- Dell: when the supported Dell BIOS provider/interface is available, query the documented `IsAdminPasswordSet`/equivalent state. Do not install Dell tooling solely for this check.
- HP: use the supported local HP BIOS WMI/management interface or an already-installed supported HP configuration provider to read configuration/password-state metadata. Do not install HP BCU/CMSL solely for this check.
- other OEM: `Unknown` until an explicit reviewed adapter is added.

The generic SMBIOS `Win32_BIOS` object is not sufficient evidence that a BIOS setup password exists.

### Secret-handling invariant

The application never reads, prompts for, stores, hashes, transmits or exports the firmware password itself. Reports contain only boolean/state evidence and the vendor source.

### Critical override

A proven missing BIOS administrative password caps the displayed security band at `Needs attention`. It does not cap at `Low` because BitLocker/Secure Boot still materially protect data/boot integrity, but the firmware configuration remains locally modifiable.

## `SEC-BOOT-RESTRICTIONS`

### Security intent

Prevent an attacker or user from booting an alternate operating system or recovery environment from removable/network media and bypassing the expected corporate Windows boot path.

The desired baseline is:

1. machine uses UEFI mode;
2. Windows Boot Manager for the currently running Windows system disk is the approved active normal boot target;
3. removable USB boot is disabled/inactive;
4. PXE/network boot is disabled/inactive;
5. optical/CD/DVD boot is disabled/inactive when present;
6. SD/removable-media boot is disabled/inactive when present;
7. other vendor/UEFI-shell/external-device boot entries are disabled/inactive unless explicitly classified as part of the approved Windows recovery path;
8. where the OEM exposes a distinct one-time/F12 boot enable policy, external one-time boot capability must also be disabled to receive `Pass`.

Merely placing the internal disk first while USB/PXE remains enabled is not full compliance.

### Evidence hierarchy

1. **Vendor firmware provider** — preferred because it can expose boot-device enable/disable state in addition to order.
2. **Windows firmware BCD view** — may confirm Windows Boot Manager order/identity but is insufficient by itself to prove that USB/PXE/one-time boot is disabled.
3. Generic SMBIOS/registry information is supporting evidence only.

### Vendor adapters

- Lenovo: enumerate documented BIOS settings/boot order through the Lenovo WMI BIOS interface; normalize actual model-specific setting names rather than assuming one global string.
- Dell: use the installed/supported Dell BIOS provider to read `BootSequence`, active device state and boot mode where exposed.
- HP: use the supported local HP BIOS provider/configuration interface to read boot order and device-enabled settings where exposed.
- unsupported/unknown OEM: do not infer `Pass` from Windows Boot Manager merely being first.

### Evaluation

- `Pass` — trusted evidence proves approved internal Windows Boot Manager/system-disk boot only, with external/removable/network alternatives disabled/inactive;
- `Warn` — Windows Boot Manager/internal disk is first, but an external/removable/network path remains enabled later in the sequence or the one-time external boot path is known to remain available;
- `Fail` — external/removable/network boot is explicitly enabled ahead of/alongside the approved path in a way that violates the baseline, Legacy boot is active, or the normal approved internal Windows path is not the effective boot target;
- `Unknown` — order is partially visible but disable-state/alternate-boot capability cannot be established reliably.

### Critical override

`Fail` caps the displayed band at `Needs attention`. `Unknown` affects coverage only.

### No automatic firmware mutation

0.17.0 never changes boot sequence, boot-device enable state, F12/one-time boot, Legacy/UEFI mode or related firmware policy. These changes are manual/central-management tasks because a mistake can render the endpoint unbootable or break deployment/recovery processes.

## Disk encryption

The previous single `SEC-BITLOCKER` control is split into OS and fixed-data controls.

### `SEC-BITLOCKER-OS` — 8

Evaluate the actual Windows operating-system volume, normally `C:` but discovered dynamically rather than hard-coded.

- `Pass` — BitLocker/device encryption reports protection `On` and the volume is fully protected/encrypted according to Windows BitLocker state;
- `Warn` — encryption is actively in progress, protection is suspended, or another temporary degraded state is positively reported;
- `Fail` — protection is off or the OS volume is fully decrypted/unprotected;
- `Unknown` — state cannot be obtained reliably.

A proven unencrypted/unprotected OS volume caps the displayed security band at `Low`.

### `SEC-BITLOCKER-DATA` — 5

Enumerate all **fixed internal data volumes** that can contain user/corporate data. Exclude EFI System Partition, Microsoft Reserved partition, Windows Recovery/OEM recovery partitions, optical media, removable USB/SD devices and other volumes positively classified as non-data/system-support partitions.

Evaluation is aggregate:

- `Pass` — every applicable fixed internal data volume is protected by BitLocker/device encryption;
- `Warn` — every applicable volume is protected or encrypting, but at least one is suspended/encryption-in-progress;
- `Fail` — at least one applicable fixed internal data volume is fully decrypted/unprotected;
- `NotApplicable` — the machine has no applicable fixed internal data volume besides the OS volume;
- `Unknown` — volume classification or BitLocker state is incomplete enough that a trustworthy aggregate cannot be produced.

The Security tab also shows each applicable volume separately as evidence so an aggregate `Fail` identifies the exact drive/volume without exposing recovery material.

### Encryption evidence

Use Windows BitLocker state (`Get-BitLockerVolume` semantics and/or the underlying supported BitLocker WMI provider) to collect at least:

- mount point/volume identity;
- volume type;
- volume/encryption status;
- encryption percentage;
- protection status;
- encryption method;
- protector **types only** where useful.

Never collect or export recovery passwords, recovery keys, external key material or protector secrets.

### No automatic BitLocker enablement

The blue hardening batch does not enable BitLocker in 0.17.0. Correct enablement requires an approved recovery-key escrow/control path (for example AD DS/Entra/enterprise management), policy-aware protector selection and reboot/recovery planning. The tool provides a remediation recommendation, not an unmanaged local encryption workflow.

A failed `SEC-BITLOCKER-DATA` caps the displayed band at `Needs attention`; a failed OS-volume control caps at `Low`.

## Security tab presentation

Add/retain rows for:

- BIOS/UEFI setup password;
- Power-on password (supplemental, unweighted);
- HDD/drive firmware password (supplemental, unweighted; informational only);
- firmware mode UEFI/Legacy;
- Windows Boot Manager target/order;
- USB boot state;
- PXE/network boot state;
- optical/removable/SD boot state when present;
- one-time/external boot capability when the vendor exposes it;
- OS-volume BitLocker state;
- each applicable fixed data volume BitLocker state;
- aggregate fixed-data encryption control.

The operator should be able to distinguish `Fail` from `Unknown` and should see the evidence source (`Windows`, `Lenovo WMI`, `Dell BIOS Provider`, `HP BIOS Provider`, etc.).

## Security hardening boundary

These new controls are **assessment/manual-remediation only** in 0.17.0. `Harden security` must not:

- set/change/clear BIOS/UEFI passwords;
- ask the operator for a BIOS password;
- change firmware boot order or boot-device enablement;
- disable PXE/USB through free-form OEM settings;
- enable/suspend/resume/decrypt BitLocker;
- add/remove/backup/rotate BitLocker protectors;
- read/export BitLocker recovery material.

They produce precise operator guidance such as `Set BIOS Supervisor/Admin password through approved OEM/management process`, `Restrict external boot through approved firmware management`, or `Enable BitLocker through the corporate key-escrow policy`.

Add RED→GREEN test groups for:

2. Dell admin-password state: set/not set/unsupported synthetic provider results;
3. HP adapter supported/unsupported synthetic results;

8. partial BCD-only evidence → `Unknown`, never `Pass`;
9. OS volume encrypted/suspended/decrypted/unknown;
10. multiple fixed volumes all protected → `Pass`;
11. one unprotected fixed data volume → aggregate `Fail`;
12. no extra fixed data volume → `NotApplicable`;
13. recovery/EFI/removable volumes excluded from fixed-data aggregate;
14. no recovery key/password appears in model, HTML, JSON or logs;
15. firmware/storage critical overrides and security-coverage math;
16. RU/EN names/evidence framing without translating stable IDs or raw OEM values.

## Windows 11 pilot additions

Pilot acceptance adds at least:

- supported Lenovo/Dell/HP firmware adapters where hardware is available;
- BIOS administrative password set and absent fixtures on disposable/test hardware or vendor-approved synthetic fixtures;
- Windows Boot Manager only and external-boot-enabled fixtures;
- multiple internal fixed volumes with protected/unprotected combinations;
- verification that no firmware secret or BitLocker recovery material is collected.

No production endpoint should have a firmware password removed, Secure Boot disabled or BitLocker disabled merely to manufacture a failing test.
