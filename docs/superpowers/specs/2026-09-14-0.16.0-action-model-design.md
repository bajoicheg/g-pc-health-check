# 0.16.0 — Service Desk action model and batch UX

## Scope

This sub-spec defines the stable action registry, recommendation/selection semantics and operator UX for:

- **Выбрать все доступные / Select all available**;
- green **Сделать хорошо / Make it better**;
- red **Сделать всё / Do everything**;
- shared preflight, confirmation and result presentation.

The exact remediation handlers are defined in the remediation sub-spec.

## Why a registry is required

0.15.x keeps action metadata in several places: `AssessmentService`, `ExecutionPolicy`, `RemediationWorker` allow-lists/switches and UI presentation. 0.16.0 adds enough actions that parallel string lists would become a security and maintenance risk.

Introduce one code-owned registry of immutable descriptors. It is the source of truth for static action metadata, while runtime availability remains a separate policy decision.

A descriptor must have stable, non-localized fields equivalent to:

- `Id` — stable machine identifier;
- `ExecutionHost` — current user process, elevated worker, or split/orchestrated;
- `RequiresAdministrator`;
- `IncludeInDoEverything`;
- `RiskLevel` — Low / Medium / High / Disruptive;
- `Order`/phase metadata;
- `MayRequireReboot`;
- `MayBreakConnectivity`;
- `MayDeleteUserVisibleState` (for example queued print jobs, never credentials/profiles);
- localization keys for title, short impact, risk explanation and verification guidance.

Do not put arbitrary executable names/arguments from UI state into descriptors. Concrete handlers stay fixed in code.

Registry validation fails tests when:

- IDs are duplicated;
- an ID has no handler/execution policy;
- a worker action is not in the worker allow-list generated/validated from registry metadata;
- an action marked `IncludeInDoEverything` has no risk/impact text;
- any prohibited protection-disable action is present.

## Stable recommendation semantics

Do not use localized `Kind` text such as `Рекомендуется` as program logic.

Add a stable recommendation classification:

- `Recommended`;
- `Optional`;
- `Manual`.

`ActionRecommendation` may keep a localized display label, but selection logic uses the stable classification.

The existing assessment decides whether an action is Recommended/Optional/Manual. The registry supplies static metadata (title/risk/admin/verification). Assessment-specific `Reason` stays contextual and localizable.

## Dynamic availability

Runtime availability remains based on freshly captured execution context immediately before execution. Saved scan context is evidence, not authorization.

Preflight produces one item per requested action with:

- descriptor;
- recommendation state when applicable;
- runtime `Ready`, `NeedsUac` or `Unavailable`;
- target scope;
- localized reason;
- whether the action will run, be skipped, or is superseded/coalesced by another requested action.

A scan can become stale between display and execution. The preflight shown in the confirmation dialog is therefore authoritative for what will be attempted.

## Existing checkbox workflow

Keep **Применить выбранное / Apply selected** for deliberate subset execution.

Add a real checkbox **Выбрать все доступные / Select all available** near the recommendations grid.

When checked, it selects every row for which:

- `CanAutomate == true`;
- current runtime availability `CanRequest == true`;
- stable recommendation class is not Manual.

Unavailable/manual rows remain unselected/read-only. When the Select All checkbox is cleared, all automated row selections are cleared. Manual rows are never modified. If the engineer manually changes an individual automated row after Select All, recompute the Select All checkbox (`checked` only when all currently requestable automated rows are selected) without recursively firing selection loops.

The existing selected-count button text remains synchronized with programmatic Select All changes.

## Green button — Make it better

The green button requests only current recommendations meeting all of:

- stable recommendation class `Recommended`;
- `CanAutomate == true`;
- registry action exists;
- runtime preflight says requestable.

It never includes Optional actions solely because they exist in the registry.

Based on the currently captured context, disable the green button when no Recommended automated action is requestable. Because context can change after rendering, clicking an enabled button still reruns preflight; if nothing remains requestable, show a non-modifying explanation and do not show UAC.

### Green confirmation

One confirmation appears before any modification. It contains:

- heading **Вы уверены? / Are you sure?**;
- list of actions that will run;
- recommended actions that will be skipped/unavailable, with reason;
- highest batch risk and concise impact;
- UAC required: yes/no;
- statement that the original GUI process will repeat diagnostics afterwards.

Cancel means no action, no UAC and no partial result.

## Red button — Do everything

The red button requests every registry descriptor with `IncludeInDoEverything == true`, regardless of current recommendation.

“Everything” means the exact 0.16.0 fixed allow-list defined in the remediation spec. It does not mean “any repair command available on Windows”.

Dynamic preflight may still mark an action unavailable because of factual context (for example CleanTemp when the main process is already elevated or the session user cannot be proven). Unavailable actions are shown before confirmation and recorded as skipped; they do not cause the entire red batch to be rejected.

### Red confirmation

The dialog is visually and textually stronger than green and contains:

- heading **Сделать всё? / Do everything?** plus **Вы уверены? / Are you sure?**;
- every requested action in execution/phase order;
- which actions are unavailable/superseded and why;
- highest risk = at least `Disruptive` when network-reset actions are runnable;
- explicit warning that VPN/RDP/network can be interrupted;
- explicit warning that pending print jobs can be deleted;
- explicit warning that Group Policy/services can refresh/restart;
- explicit warning that DISM/SFC may take a long time;
- explicit warning that reboot may be required afterwards but will not be forced;
- explicit statement that security software is not disabled or weakened.

Cancel means no changes and no UAC.

After confirmation there are no extra application confirmation dialogs for individual actions. Native commands must be invoked in non-interactive forms where possible so hidden prompts cannot become a second ambiguous confirmation path.

## One-UAC rule and phases

For a batch containing administrative actions, request elevation once and reuse one authenticated elevated-worker lifetime for all worker-hosted actions.

Do not spawn one UAC prompt per action.

If the GUI already has a confirmed administrative token, do not generate a pointless second UAC prompt. In this case user-context-only actions such as CleanTemp may still be unavailable because elevation itself changes their safety boundary.

If UAC is cancelled or the elevated worker cannot authenticate/connect, no worker or parent mutating action is executed.

For the red batch, the worker uses the phased authenticated protocol defined in `2026-09-14-0.16.0-remediation-design.md`: elevated non-network actions → authenticated checkpoint → original-user actions that must precede network disruption → elevated network-disruptive actions → final current-process cache action. Every transition remains bound to the same session/nonce. This preserves alternate-admin identity boundaries while still using one UAC.

## Batch modes

Use explicit orchestration modes rather than one boolean:

- `SelectedStrict` — current Apply Selected behavior; if a selected request becomes invalid, stop before execution and ask the engineer to re-evaluate selection.
- `RecommendedBestEffort` — green; run all requestable Recommended automated actions and record non-runnable recommended items.
- `AllBestEffort` — red; request the entire fixed all-set, run what is safely requestable and record skipped/unavailable/superseded items.

Best-effort does not mean ignore failures. Each attempted action has a result; overall batch outcome becomes `Complete`, `Partial`, `Failed` or `Cancelled` according to deterministic rules.

## Coalescing and superseding

Some broad actions subsume narrower ones. The preflight may coalesce to avoid pointless duplicate side effects while still recording every requested action.

Required example:

- `ClearPrintQueue` performs a controlled Spooler stop/start as part of queue clearing. When both `RestartSpooler` and `ClearPrintQueue` are requested, run the broader queue-clear sequence once and mark the standalone restart as `Superseded`/satisfied by `ClearPrintQueue` rather than stopping/starting the service twice.

Coalescing decisions are fixed in code and surfaced in confirmation/evidence; they are not inferred from translated text.

## Main window layout

Keep the existing recommendations grid and selected-action button. Add the two batch buttons close enough to be understood as alternatives but visually distinct:

- green filled button: **Сделать хорошо / Make it better**;
- red filled button: **Сделать всё / Do everything**.

They must not be adjacent in a way that makes accidental red activation easy without the subsequent strong confirmation. Keyboard focus/default-button behavior must not make the red button the default Enter action.

At DPI 100/150/200, buttons and confirmation text must remain visible without clipping.

## Result presentation

After a batch:

- preserve per-action results, skipped/superseded items and warnings;
- run the existing follow-up diagnostic scan in the original GUI process when the UI remains connected;
- show before/after score/coverage/findings without claiming causality;
- show a prominent `reboot may be required` marker if any executed action sets it;
- for connectivity-breaking actions, acknowledge that the operator may lose the interactive session before viewing final UI.

Command exit code 0 means the command reported success, not that the user's symptom is resolved.

## Test-first requirements

Focused RED tests must cover at minimum:

- registry ID uniqueness and handler coverage;
- no translated display string used as action-selection logic;
- Select All checks/clears exactly requestable automated rows and stays synchronized after manual row edits;
- green set = Recommended + automated + requestable only;
- green no-op after stale preflight produces no UAC/action call;
- red set = exact `IncludeInDoEverything` registry set;
- unavailable red actions become visible skipped items instead of aborting the whole batch;
- selected-strict still rejects stale invalid selection before modification;
- confirmation cancel produces zero executor/UAC calls;
- one administrative batch produces exactly one elevation-worker start;
- already-elevated batch does not spawn a second UAC;
- phased red batch uses one authenticated session/nonce through every transition;
- coalescing of ClearPrintQueue/RestartSpooler;
- highest-risk/impact aggregation;
- red confirmation contains network/RDP/VPN, print-job, policy/service, duration, reboot and protection-preservation warnings in RU and EN;
- red button is not the default Enter action;
- all prior worker/session/nonce/portable tests remain green.

No hosted-CI test executes real network resets, service restarts, queue deletion, DISM/SFC or policy refresh. Use injected/fake action executors for batch behavior and the existing negative worker process tests for protocol enforcement.
