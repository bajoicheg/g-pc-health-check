# 0.17.0 — Local administrators allow-list policy

This component specification extends the approved 0.17.0 Endpoint Security Posture design. It adds a centrally managed local-administrator control while preserving the single-portable-EXE endpoint experience.

## Intent

Add a weighted security control, `SEC-LOCAL-ADMINS`, which verifies that every direct principal in the local Windows **Administrators** group is explicitly permitted by a centrally managed machine allow-list.

The control is assessment-only in 0.17.0. G PC Health Check does not add/remove users or groups from local Administrators and the blue `Усилить защиту / Harden security` batch does not modify local group membership.

## Endpoint packaging and policy source

The endpoint remains a single portable EXE. No JSON/INI/config file is required beside the executable.

The authoritative policy source is machine-level Registry policy:

- key: `HKLM\SOFTWARE\Policies\GPCHealthCheck`
- value: `AllowedLocalAdministrators`
- type: `REG_MULTI_SZ`
- one allow-list pattern per string

The application reads this value only. It never creates, edits or deletes the policy value.

The existing per-user `settings.json` remains only for user preferences such as language and MUST NOT be used as a fallback security-policy source.

### Policy absence and invalid policy

- value present with valid `REG_MULTI_SZ` data, including an intentionally empty list: evaluate the configured allow-list;
- value missing: `SEC-LOCAL-ADMINS = Unknown` with evidence `machine policy not configured`;
- value present with the wrong Registry type or unreadable data: `Unknown` with bounded collection evidence;
- blank/whitespace-only strings inside a valid list are ignored;
- duplicate normalized patterns are harmless and are de-duplicated for evaluation/presentation.

An explicitly configured empty effective list means **no direct principal is allowed**; any actual direct member therefore makes the control `Fail`.

## ADMX / ADML administration

Ship administrative templates for central management, separate from the endpoint runtime binary:

- `GPCHealthCheck.admx`;
- localized `GPCHealthCheck.adml` resources (RU and EN).

These are administrator/deployment artifacts, not endpoint runtime dependencies. They may be copied to the organization's Group Policy Central Store; clients receive only the resulting Registry policy through normal Group Policy processing.

The ADMX policy is machine-scoped and exposes a multi-line list editor:

**Computer Configuration → Administrative Templates → G PC Health Check → Security Posture → Allowed local administrators**

Use an ADMX `multiText` element bound to `AllowedLocalAdministrators`, which maps to `REG_MULTI_SZ`. Disabling or leaving the policy Not Configured removes/omits the value according to normal Administrative Template semantics; the application then reports `Unknown`, not `Pass`.

The template help text documents wildcard semantics and examples. The application remains the authority for validation/evaluation; ADMX is only the administrative UI and Registry delivery contract.

## Administrators-group discovery

Do not locate the group by localized display name. Resolve/enumerate the local built-in Administrators group by well-known SID:

`S-1-5-32-544`

Enumerate **direct members** only. Each observed member preserves at least:

- SID;
- resolved account/principal name when available;
- object class/type where available (`User`, `Group`, `Unknown`);
- principal source where available (`Local`, `ActiveDirectory`, `MicrosoftAccount`, `AzureAD`/equivalent, `Unknown`);
- name-resolution status.

Users and groups are both principals and are both checked against the allow-list. An allowed AD/domain group is accepted as one direct principal; 0.17.0 does not recursively expand its remote membership. The UI explicitly notes that nested/domain group membership is governed outside this local check.

## Principal normalization

A member can be matched by either its normalized name or its SID representation.

### Names

Use a stable case-insensitive canonical form:

- domain/enterprise principal: `DOMAIN\name` as resolved by Windows;
- local principal: normalize the current computer-name prefix to `LOCAL\name` so the same policy works across computers;
- provider-specific names that cannot be safely normalized remain in their Windows-provided canonical form.

No environment-variable expansion is performed.

### SID form

Every known SID also has the candidate representation:

`SID:<canonical-sid>`

Example for the built-in local Administrator account regardless of rename/computer SID:

`SID:S-1-5-21-*-500`

The program never treats a display name as stronger evidence than a SID.

## Wildcard language

The allow-list intentionally supports a small deterministic glob language only:

- `*` — matches zero or more characters;
- `?` — matches exactly one character;
- every other character is literal;
- matching is case-insensitive;
- matching is anchored to the entire normalized candidate string;
- `\` is a literal principal separator;
- there are no regular expressions, character classes, alternation, environment-variable expansion or implicit substring matching.

Examples:

- `CONTOSO\adm-*` matches `CONTOSO\adm-alex` and `CONTOSO\adm-`;
- `CONTOSO\adm-????` matches exactly four characters after `adm-`;
- `CONTOSO\svc?ops` matches `CONTOSO\svc1ops` but not `CONTOSO\svc12ops`;
- `LOCAL\Administrator` matches that exact local account name after local-prefix normalization;
- `SID:S-1-5-21-*-500` matches the built-in local Administrator account by SID even if renamed.

Patterns are matched using a bounded deterministic glob matcher, not by evaluating administrator-supplied text as arbitrary regular expressions.

## Member evaluation

For each direct member:

1. if any allow-list pattern matches the canonical `SID:` candidate, the member is `Allowed` even when name resolution fails;
2. otherwise, if the name is resolved and any pattern matches the normalized name candidate, the member is `Allowed`;
3. if the name is resolved and no SID/name pattern matches, the member is `Unauthorized`;
4. if name resolution failed, the SID is known, no SID rule matched, and name-based rules exist that cannot be evaluated without a name, the member is `Unknown` rather than a false `Unauthorized`;
5. if neither a trustworthy SID nor name can be obtained, the member is `Unknown`.

Aggregate `SEC-LOCAL-ADMINS` status:

- `Pass` — policy is valid and every direct member is `Allowed`;
- `Fail` — at least one direct member is conclusively `Unauthorized`;
- `Unknown` — no conclusive unauthorized member exists, but the policy/collection/member resolution is incomplete;
- `NotApplicable` is not used for a Windows 11 endpoint because the built-in Administrators group is an applicable control.

If both `Unauthorized` and `Unknown` members exist, aggregate status is `Fail`, while unresolved members remain visible as additional incomplete evidence.

## Security score

`SEC-LOCAL-ADMINS` weight: **8 points**.

Because Endpoint Security Posture v1 remains exactly 100 points, this component supersedes only the previous firmware/storage weighted-control table with the following final 0.17.0 allocation:

| ID | Control | Weight |
|---|---|---:|
| `SEC-AV-ACTIVE` | active primary antivirus/EPP | 9 |
| `SEC-AV-PLATFORM` | AV platform/product update status when provable locally | 2 |
| `SEC-AV-DEFINITIONS` | malware definitions/signatures current | 8 |
| `SEC-AV-RTP` | real-time/protection components active | 8 |
| `SEC-AV-TAMPER` | tamper/self-protection where trustworthy local state exists | 3 |
| `SEC-FIREWALL` | effective host firewall protection | 11 |
| `SEC-OS-UPDATES` | Windows security/quality update posture | 10 |
| `SEC-BITLOCKER-OS` | Windows system volume protected | 8 |
| `SEC-BITLOCKER-DATA` | all applicable fixed internal data volumes protected | 5 |
| `SEC-SECUREBOOT` | Secure Boot enabled | 6 |
| `SEC-BIOS-ADMIN-PASSWORD` | BIOS/UEFI administrative configuration password set | 5 |
| `SEC-BOOT-RESTRICTIONS` | approved internal Windows boot path only | 4 |
| `SEC-UAC` | UAC enabled | 4 |
| `SEC-TPM` | TPM present/ready/2.x | 4 |
| `SEC-VBS-HVCI` | VBS / Memory Integrity runtime posture | 5 |

Total: **100**.

Existing `Pass/Warn/Fail/Unknown` score and coverage math is unchanged. `SEC-LOCAL-ADMINS` does not use `Warn`: membership is either proven compliant, proven unauthorized, or incompletely known.

### Critical override

A confirmed unauthorized direct local administrator is a critical endpoint-control failure and caps the displayed Security band at **Low**, regardless of arithmetic score.

Missing/unreadable policy or unresolved membership does not create a false `Low`; it produces `Unknown`, lowers Security coverage and can trigger `Assessment incomplete` under the existing coverage rules.

## Security-tab presentation

The Security tab shows the aggregate control plus a per-principal detail table with at least:

- Principal;
- Type;
- SID;
- Source;
- Result (`Allowed`, `Unauthorized`, `Unknown`);
- matched allow-list rule when allowed;
- evidence/reason.

The policy source is displayed as `HKLM machine policy / Group Policy` without exposing unrelated Registry data.

Patterns may be shown to a Service Desk operator because they are policy metadata, but the application provides no edit button and no write path.

## Reporting

HTML/JSON evidence includes:

- whether the machine policy was configured/read successfully;
- normalized effective allow-list patterns;
- each direct member's SID/name/type/source/result;
- matched rule where applicable;
- aggregate control status and score contribution;
- collection warnings.

Do not enumerate remote/nested group membership in 0.17.0. Do not export tokens, credentials or unrelated account attributes.

## Hardening boundary

`Усилить защиту / Harden security` does **not** automatically remove unauthorized administrators in 0.17.0.

Reason: an incorrect allow-list or stale domain state could remove legitimate Service Desk/management access. The application provides exact evidence and remediation guidance such as `Remove unauthorized principal through approved Group Policy/endpoint-management process`.

No generic local-group mutation API is added to the GUI or worker protocol.

## Pilot acceptance

Managed Windows 11 pilot includes:

- policy delivered through ADMX-backed GPO;
- exact-user rule;
- domain-group rule;
- `*` and `?` wildcard cases;
- renamed built-in Administrator allowed by SID;
- unauthorized direct domain/local user fixture on a disposable/test endpoint;
- orphaned/unresolved SID fixture where practical;
- standard-user execution that can read the machine policy and group membership;
- proof that removing ADMX/ADML from the endpoint has no effect after policy has been written to Registry;
- proof that the portable EXE still runs without any adjacent config file.

Production endpoints must not have legitimate administrator access intentionally removed merely to manufacture a failing pilot case.
