# 0.17.0 — Endpoint Security Posture and safe hardening

## Intent

0.17.0 adds an explicit endpoint-security posture layer to G PC Health Check without changing the meaning of the existing technical Health Score. A workstation can be technically healthy while being insecure, or secure while suffering performance/storage faults; therefore the two scores remain independent.

The release adds four owner-approved product capabilities:

1. a read-only **Endpoint Security Posture** assessment for Windows 11;
2. a separate **ИБ / Security** score and coverage indicator visible immediately on the main window;
3. a dedicated **ИБ / Security** tab with per-control status, evidence, score contribution and operator guidance;
4. a third Service Desk batch button, **Усилить защиту / Harden security**, for a small fixed allow-list of safe security improvements.

The existing green **Сделать хорошо / Make it better** and red **Сделать всё / Do everything** flows remain semantically unchanged. The new security flow must never become a generic configuration engine and must never disable, weaken, exclude, uninstall or bypass security controls.

## Product terminology and UX

The three high-level Service Desk buttons are deliberately differentiated by purpose, color and risk:

| Order | RU | EN | Color | Meaning |
|---|---|---|---|---|
| 1 | **Усилить защиту** | **Harden security** | blue `#2386C0` | only explicitly supported security hardening actions |
| 2 | **Сделать хорошо** | **Make it better** | green `#177A4B` | recommended routine workstation remediation |
| 3 | **Сделать всё** | **Do everything** | red `#B53636` | fixed comprehensive remediation batch including disruptive actions |

The visual order is always blue → green → red. Red remains the rightmost high-risk action and must never become the default Enter action. Blue is not described as “make compliant” because the program cannot certify organization-wide compliance from a local snapshot.

## Main-window metrics

The main metric strip grows from six to seven cards:

1. `ИНДЕКС / SCORE` — existing technical Health Score;
2. `ИБ / SECURITY` — new security posture score;
3. `ПОКРЫТИЕ / COVERAGE` — existing diagnostic coverage;
4. CPU;
5. RAM;
6. system disk;
7. uptime.

The Security card shows:

- numeric score `0–100` when at least one weighted security control is known;
- qualitative band;
- security telemetry coverage, for example `84 / 100 · хороший · проверено 91%`;
- a neutral/amber incomplete state when coverage is below the trustworthy threshold.

Clicking the card selects the dedicated Security tab.

The existing technical score, technical coverage and their thresholds are not recalculated from security findings.

## Security score model

### Weighted controls

The baseline is named **Endpoint Security Posture v1** and has 100 possible weighted points:

| ID | Control | Weight |
|---|---|---:|
| `SEC-AV-ACTIVE` | active primary antivirus/EPP | 10 |
| `SEC-AV-PLATFORM` | AV platform/product update status when provable locally | 5 |
| `SEC-AV-DEFINITIONS` | malware definitions/signatures current | 10 |
| `SEC-AV-RTP` | real-time/protection components active | 10 |
| `SEC-AV-TAMPER` | tamper/self-protection where the provider exposes trustworthy local state | 5 |
| `SEC-FIREWALL` | effective host firewall protection | 15 |
| `SEC-OS-UPDATES` | Windows security/quality update posture | 15 |
| `SEC-BITLOCKER` | Windows system volume protected by BitLocker | 8 |
| `SEC-SECUREBOOT` | Secure Boot enabled | 7 |
| `SEC-UAC` | UAC enabled (`EnableLUA`) | 5 |
| `SEC-TPM` | TPM present, ready and TPM 2.x capability confirmed where available | 5 |
| `SEC-VBS-HVCI` | VBS / Memory Integrity runtime posture | 5 |

The sum of all configured weights is exactly 100.

### Status values

Each control has one stable machine status:

- `Pass` — evidence proves the baseline requirement is met;
- `Warn` — protection exists but currency/configuration is degraded or a non-critical remediation is pending;
- `Fail` — evidence proves a required protection is disabled/missing/stale beyond the fail threshold;
- `Unknown` — the collector cannot establish the state reliably;
- `NotApplicable` — the control genuinely does not apply to the detected platform/provider.

`Unknown` is never converted to `Pass`. Raw provider strings remain raw evidence; localized status text is presentation only.

### Coverage and score calculation

Security coverage is independent from existing diagnostic coverage.

For weighted controls:

- `Pass`, `Warn` and `Fail` count as **known**;
- `Unknown` is excluded from the known denominator and lowers coverage;
- `NotApplicable` is removed from both numerator and denominator only when the evaluator can prove it is genuinely not applicable.

`SecurityCoveragePercent = known applicable weight / total applicable weight × 100`.

The visible score is normalized over known applicable controls rather than treating unknowns as zero:

- `Pass` earns 100% of the control weight;
- `Warn` earns 50% of the control weight;
- `Fail` earns 0%;
- normalized result is scaled to 0–100 over the known applicable weight.

This prevents data-access failures from looking like insecure settings while also preventing missing telemetry from looking healthy.

### Trust threshold and bands

If security coverage is below **80%**, the card is presented as **Оценка неполная / Assessment incomplete** regardless of the numeric score. The numeric value may still be shown for troubleshooting but must not receive a green “high/good” presentation.

When coverage is at least 80%:

- `90–100` — **Высокий / High**;
- `75–89` — **Хороший / Good**;
- `50–74` — **Требует внимания / Needs attention**;
- `0–49` — **Низкий / Low**.

### Critical overrides

The qualitative band is capped independently of arithmetic when a critical control fails:

- primary antivirus/EPP confirmed disabled/expired/snoozed → no better than `Low`;
- effective host firewall confirmed absent/disabled → no better than `Low`;
- qualifying Windows security/quality update posture confirmed severely stale (>60 days since last successful qualifying update) → no better than `Needs attention`;
- UAC confirmed disabled → no better than `Needs attention`.

Critical overrides change the displayed band, not the raw normalized score; reports retain both.

## Control evaluation details

### Antivirus/EPP provider discovery

Windows Security Center is the vendor-neutral first source on Windows 11 desktop systems. The collector enumerates registered antivirus and firewall products through Windows Security Center interfaces and preserves:

- provider/product name;
- product state (`ON`, `OFF`, `SNOOZED`, `EXPIRED`);
- signature status (`UP_TO_DATE`, `OUT_OF_DATE`) where exposed;
- source/provider type.

Provider-specific enrichment is allowed only from a fixed supported provider list. Version 0.17.0 initially supports:

- Microsoft Defender;
- Kaspersky Endpoint Security for Windows;
- generic Windows Security Center fallback for other vendors.

Multiple registered AV products are not scored by requiring every product to be `ON`. The evaluator determines an **effective primary active provider**. A passive Defender entry alongside an active Kaspersky installation must not produce a false failure.

If provider selection is ambiguous, primary-provider-dependent controls become `Unknown`, not `Pass` or `Fail`.

### `SEC-AV-ACTIVE` — 10

- `Pass`: an effective primary antivirus/EPP is reported `ON` and not expired;
- `Warn`: protection is present but a provider-specific degraded state is proven without complete shutdown;
- `Fail`: selected primary provider is `OFF`, `SNOOZED` or `EXPIRED`, or Windows Security Center explicitly reports no effective antivirus protection;
- `Unknown`: provider discovery is unavailable or conflicting.

### `SEC-AV-PLATFORM` — 5

The program must not claim that an antivirus binary is “the latest version” merely because it can read a version number. No internet lookup or cloud dependency is added in 0.17.0.

- collect local product/platform/engine version where the provider exposes it;
- `Pass` only when a local provider/API can positively prove current/non-expired platform state or when a qualifying platform update is confirmed through the configured Windows update source;
- `Fail` only when local evidence explicitly reports expired/obsolete platform state;
- otherwise `Unknown`.

This control intentionally reduces security coverage on vendors where product-version compliance cannot be established locally. A future organization policy baseline may add explicit minimum versions, but 0.17.0 does not hard-code Gradient-specific product versions into a public generic binary.

### `SEC-AV-DEFINITIONS` — 10

Primary source is provider-reported signature status. When a reliable timestamp is available it enriches the result:

- explicit `OUT_OF_DATE` → `Fail`;
- explicit `UP_TO_DATE` and definition age `≤2 days` → `Pass`;
- definition age `3–7 days` with no explicit out-of-date state → `Warn`;
- definition age `>7 days` → `Fail`;
- no trustworthy signature state/time → `Unknown`.

For Defender, use read-only status from the Defender module / native data exposed by `Get-MpComputerStatus` semantics. For Kaspersky, use the fixed installed `kescli --opswat GetDefinitionState` interface when available.

### `SEC-AV-RTP` — 10

This is a provider-specific composite of protection components that are meaningful for the active primary provider.

Defender enrichment may include, when available, real-time protection, on-access/IOAV and behavior monitoring. Kaspersky enrichment uses the supported File Threat Protection state (`kescli --opswat GetRealTimeProtectionState`) and may include other provider states only when exposed through a documented fixed interface.

- all required observable provider components active → `Pass`;
- some optional/enrichment component degraded while core RTP remains active → `Warn`;
- core real-time protection confirmed disabled → `Fail`;
- provider does not expose sufficient state → `Unknown`.

### `SEC-AV-TAMPER` — 5

- `Pass`: active provider explicitly reports tamper/self-protection active;
- `Fail`: active provider explicitly reports the control disabled and the product defines it as an applicable protection;
- `Unknown`: no trustworthy local interface exists;
- `NotApplicable`: only when the provider explicitly has no corresponding feature.

For Defender this can use the locally exposed tamper-protection status when available. The program must not attempt to disable or bypass tamper protection.

### `SEC-FIREWALL` — 15

Use Windows Security Center effective firewall registration first and Windows Firewall ActiveStore profile details second.

Rules:

- active third-party firewall registered and protecting → `Pass`; Windows Defender Firewall profile state is shown as evidence but does not cause a false failure merely because a third-party firewall intentionally owns the function;
- Microsoft Defender Firewall is the effective provider → Domain/Private/Public profile settings are read from the ActiveStore; all enabled → `Pass`, a provably disabled profile → `Fail`;
- no effective firewall provider → `Fail`;
- ambiguous provider ownership or inaccessible state → `Unknown`.

Do not enumerate or grade individual firewall rules in 0.17.0.

### `SEC-OS-UPDATES` — 15

Windows Update assessment is local and respects the machine's configured update service (including enterprise WSUS where Windows Update Agent uses it). The program does not force Microsoft Update or change update source.

Collect:

- last successful qualifying Windows security/quality update from WUA history;
- whether applicable pending qualifying updates are found through the configured update source;
- pending reboot state from the existing diagnostics model;
- any WUA search/history errors as evidence.

Qualifying updates are security/critical/quality cumulative/update-rollup style OS updates; Defender signatures are scored separately.

Evaluation:

- no pending qualifying update and last successful qualifying update `≤45 days` → `Pass`;
- pending qualifying update exists, or last successful qualifying update is `46–60 days` old → `Warn`;
- last successful qualifying update is `>60 days` old with otherwise trustworthy WUA evidence → `Fail`;
- WUA/history/search unavailable or no trustworthy qualifying history → `Unknown`.

A newly offered Patch Tuesday update therefore produces `Warn`, not an immediate critical failure. Update installation itself is not automatic in 0.17.0.

### `SEC-BITLOCKER` — 8

Evaluate the detected Windows system volume only:

- `ProtectionStatus=On`, fully encrypted/protected → `Pass`;
- encryption in progress or protection temporarily suspended → `Warn`;
- supported system volume fully decrypted / protection off → `Fail`;
- inaccessible/unsupported state → `Unknown` or proven `NotApplicable`.

Never enable BitLocker, add/remove protectors, escrow keys or expose recovery material.

### `SEC-SECUREBOOT` — 7

Read the current Secure Boot state without prompting for UAC during the ordinary scan. Prefer a non-mutating Windows-supported local state source; an elevated-only probe is not automatically invoked just to improve coverage.

- enabled → `Pass`;
- supported but disabled → `Fail`;
- Legacy BIOS / unsupported platform proven → `NotApplicable` only if the product policy explicitly treats the hardware as outside the Secure Boot baseline; otherwise show `Fail` with unsupported-hardware evidence for Windows 11-class endpoint expectations;
- inaccessible → `Unknown`.

0.17.0 never changes UEFI/Secure Boot configuration.

### `SEC-UAC` — 5

Read `EnableLUA` semantics:

- enabled → `Pass`;
- disabled → `Fail`;
- unreadable → `Unknown`.

No automatic UAC policy modification is allowed.

### `SEC-TPM` — 5

Collect TPM presence/readiness plus TPM 2.x capability/version where exposed:

- present + ready + TPM 2.x confirmed → `Pass`;
- present but not ready/provisioned → `Warn`;
- missing or version below the Windows 11 baseline when reliably known → `Fail`;
- version/readiness not determinable → `Unknown` for the unresolved portion.

Never initialize, clear, own or reprovision TPM.

### `SEC-VBS-HVCI` — 5

Use the runtime `Win32_DeviceGuard` view where available, not only configured registry intent:

- `VirtualizationBasedSecurityStatus=2` and `SecurityServicesRunning` contains `2` (Memory Integrity/HVCI) → `Pass`;
- VBS running but HVCI not running → `Warn`;
- VBS configured but not running, or HVCI expected/configured but not running → `Warn`/`Fail` depending on explicit runtime evidence;
- both VBS and HVCI confirmed disabled on a supported Windows 11 endpoint → `Fail`;
- WMI unavailable → `Unknown`.

0.17.0 does not enable VBS/HVCI automatically because driver compatibility and reboot requirements make that inappropriate for a one-click Service Desk hardening action.

## Data model and isolation

Add a security-specific model rather than embedding security facts into `Assessment`:

- `SecurityPostureSnapshot` — raw normalized evidence and collection warnings;
- `SecurityControlResult` — stable control ID, status, weight, earned fraction, localized-independent evidence fields and guidance code;
- `SecurityPostureAssessment` — raw score, display band, coverage, critical overrides and result list;
- `SecurityHardeningRecommendation` — stable fixed action IDs and availability;
- `SecurityHardeningBatchResult` — before/after security posture plus per-action execution evidence.

`ScanResult` may reference the security snapshot/assessment, but existing `Assessment.Score`, `Assessment.Status`, `Assessment.CoveragePercent` and technical findings retain their existing meaning.

Collectors, evaluator and UI are separate units:

1. **collector** obtains facts only;
2. **evaluator** maps facts to control results deterministically;
3. **presentation** localizes labels and guidance;
4. **hardening planner/executor** consumes only fixed action IDs and fresh execution-context preflight.

The evaluator performs no native commands and has no dependency on WinForms, enabling full synthetic TDD coverage.

## Security tab

Add a top-level **ИБ / Security** tab. It contains a summary header and a grid with at least:

- Control;
- Status;
- Points;
- Evidence/fact;
- Recommendation;
- Source/coverage note.

Example rows:

| Control | Status | Points | Evidence | Recommendation |
|---|---|---:|---|---|
| Antivirus | `Pass` | `10/10` | Kaspersky Endpoint Security, ON | — |
| AV definitions | `Warn` | `5/10` | definitions 4 days old | Update definitions |
| Firewall | `Fail` | `0/15` | effective firewall protection off | Restore approved firewall protection |
| Windows Update | `Warn` | `7.5/15` | 2 qualifying updates pending | Install through corporate update channel |
| BitLocker | `Pass` | `8/8` | C: Protection On | — |

Rows with `Unknown` show no fake points and explain what evidence was unavailable.

The tab supports the existing report/export philosophy: human-readable HTML plus stable machine evidence in JSON. Sensitive data such as BitLocker recovery keys, security-product secrets or credentials are never collected.

## `Усилить защиту / Harden security` batch

### Intent

The blue button is a conservative remediation flow for high-confidence security actions only. It is not “security Do everything”. It must operate from a code-owned fixed allow-list, preflight every action, show exact planned/skipped actions, request UAC only if needed, and perform a fresh security posture scan afterwards.

### Initial action allow-list

0.17.0 permits only the following automatic hardening classes when their provider and context are positively identified:

1. `SecurityUpdateAvDefinitions`
   - update definitions for the active supported AV provider;
   - Defender: supported signature-update interface;
   - Kaspersky: fixed `kescli` database/module update command;
   - no arbitrary executable/path supplied by the UI.

2. `SecurityEnablePrimaryRtp`
   - enable real-time protection only for a positively identified supported primary provider and only through its documented fixed interface;
   - no attempt to disable another provider;
   - no policy bypass, password bypass, tamper-protection bypass or registry hacking.

3. `SecurityEnableWindowsFirewall`
   - available only when the evaluator proves Windows Defender Firewall is the intended effective firewall provider and no active third-party firewall owns that role;
   - enables the approved Windows Firewall profiles through a fixed implementation;
   - if ownership is ambiguous, action is `Unavailable`.

Every action has a stable ID, fixed implementation, risk metadata, target scope, dynamic availability and post-action verification.

### Explicitly manual in 0.17.0

The blue button must **not** automatically:

- enable or provision BitLocker;
- create/export/rotate BitLocker recovery keys;
- change Secure Boot/UEFI;
- initialize/clear/reprovision TPM;
- enable VBS/HVCI/Memory Integrity;
- install Windows quality/security updates;
- reboot or log off;
- change UAC policy;
- install/upgrade/uninstall antivirus/EDR;
- alter AV exclusions;
- stop or weaken AV/EDR/firewall;
- bypass Kaspersky Security Center policy, Defender management, GPO, MDM or tamper protection;
- change Windows Update/WSUS source;
- invoke free-form PowerShell/CMD/service/registry commands.

For these controls, the Security tab provides evidence and operator guidance only.

### Kaspersky management boundary

Kaspersky Endpoint Security support is provider enrichment, not a replacement for Kaspersky Security Center. Read-only KESCLI OPSWAT commands may enrich protection/definition state. Automatic Kaspersky changes are allowed only through fixed documented KESCLI operations and only if local policy permits the action normally.

The application must not invoke policy-disabling commands, protection-disabling commands, exclusion changes, uninstall operations or any password/policy bypass. If central policy blocks an improvement, report `BlockedByPolicy`/`Unavailable` and direct the operator to the managed channel.

## Three-button interaction rules

- Blue and green are peer “safe batch” operations but select disjoint intents: security hardening versus technical remediation.
- The blue batch is derived only from security-control recommendations; it never silently includes ordinary technical actions such as Temp cleanup or DNS reset.
- The green batch never silently includes security-policy changes simply because the new security score is low.
- Red `Do everything` remains the fixed 0.16.0 remediation set and **does not absorb the blue security-hardening actions** in 0.17.0. This is intentional: “Do everything” must not start altering endpoint security policy as a side effect.
- Any future request to merge blue actions into red requires a separate approved design change.

## Error and truthfulness semantics

- Collector errors become bounded warnings/evidence and `Unknown` controls.
- A command returning successfully does not by itself mean the security control is fixed; the program must re-collect and re-evaluate.
- `Skipped`, `BlockedByPolicy`, `Unknown` and `NotApplicable` are distinct from `Pass`.
- Security card text must not say “compliant” or “secure” as an absolute claim; use “High/Good/Needs attention/Low” and coverage.
- The application must not contact external vendor/cloud URLs solely to calculate posture in 0.17.0.

## Localization

RU/EN remains complete for:

- Security metric/card;
- Security tab controls, statuses and guidance;
- security hardening confirmation/result dialogs;
- report and clipboard human-readable text;
- provider-specific operator messages.

Stable control IDs, action IDs, JSON property names, raw provider names/versions and native evidence values are not translated.

## Reports and evidence

HTML/JSON output adds a separate security section containing:

- posture model version (`EndpointSecurityPosture-v1`);
- security raw score and displayed band;
- security coverage;
- critical overrides;
- each control ID/status/weight/earned fraction;
- bounded normalized evidence;
- collection warnings;
- before/after security hardening evidence when actions ran.

Do not collect or export:

- BitLocker recovery passwords/keys;
- AV/EDR passwords or tokens;
- credentials/cookies/browser secrets;
- arbitrary policy content not needed for the evaluated state.

## TDD and validation plan

Implementation follows RED → GREEN in isolated tasks. Minimum test groups:

1. **Pure evaluator tests**
   - all-pass 100/100;
   - mixed Pass/Warn/Fail math;
   - Unknown lowers coverage but is not scored as failure;
   - NotApplicable denominator behavior;
   - coverage <80 cannot display High/Good;
   - critical overrides for AV/firewall/OS/UAC;
   - passive Defender + active Kaspersky does not false-fail.

2. **Provider normalization tests**
   - WSC ON/OFF/SNOOZED/EXPIRED;
   - signature up-to-date/out-of-date;
   - Defender provider enrichment;
   - Kaspersky KESCLI parsing using synthetic outputs;
   - malformed/partial provider responses become Unknown.

3. **Windows-control collector tests**
   - firewall ActiveStore profile normalization;
   - WUA history/pending-update normalization;
   - system-volume BitLocker states;
   - Secure Boot supported/enabled/disabled/unknown;
   - TPM ready/not-ready/missing;
   - `EnableLUA` states;
   - `Win32_DeviceGuard` VBS/HVCI runtime states.

4. **UI/localization tests**
   - seventh metric card and Security tab in RU/EN;
   - score/band/coverage presentation;
   - blue/green/red order, exact colors and labels;
   - red is never default Enter action;
   - no Cyrillic operator framing in English mode;
   - stable IDs/raw evidence remain untranslated.

5. **Security hardening tests**
   - exact fixed allow-list;
   - unsupported/ambiguous provider cannot execute;
   - third-party firewall prevents Windows Firewall auto-enable;
   - no security weakening action exists in registry/worker;
   - no free-form executable/service/registry interface;
   - policy-blocked result is not success;
   - after-action re-evaluation required before claiming improvement.

6. **Regression/release gates**
   - all existing 0.16.0 source self-tests;
   - warnings-as-errors;
   - NuGet vulnerability audit;
   - published single EXE self-test;
   - portable EXE/worker security matrix;
   - exact-main build, release and supply-chain attestation path.

## Windows 11 pilot acceptance

Hosted Windows Server CI cannot prove actual Windows 11 security-provider behavior. Managed pilot must include at least:

- corporate Windows 11 workstation with Kaspersky Endpoint Security managed by KSC;
- Defender-primary Windows 11 workstation;
- active third-party AV + passive Defender;
- Domain/Private/Public firewall profile scenarios;
- corporate WSUS/update source and an update-pending case;
- BitLocker On / suspended or decrypting fixture where safely available;
- Secure Boot + TPM 2.0;
- VBS/HVCI enabled and disabled test fixtures;
- standard user, admin-member with UAC and already-elevated contexts;
- RU/EN and DPI/resize acceptance;
- blue hardening batch on an approved test workstation.

No pilot may intentionally disable production security controls on a corporate workstation merely to manufacture a FAIL case; synthetic fixtures or disposable test devices are used for destructive/degraded scenarios.

## Non-goals for 0.17.0

- organization-wide compliance certification;
- CIS/Microsoft Security Baseline full policy audit;
- KSC/Intune/EDR cloud integration;
- external vulnerability scanner;
- driver/firmware version compliance;
- browser hardening audit;
- local-admin membership governance;
- arbitrary GPO/registry hardening;
- automated OS patch installation;
- automatic BitLocker/Secure Boot/TPM/VBS remediation.

These can be future posture modules without changing the v1 evidence/coverage principles.

## Release target and success criteria

Target product version is **0.17.0** after implementation is complete and all release gates are green; the design commit alone does not change application version or publish assets.

0.17.0 is successful when a Service Desk engineer can immediately see a separate, truthful security-posture score and coverage on the main window, drill into exact security controls/evidence, distinguish unknown telemetry from failure, safely run the blue hardening batch for only the supported fixed actions, and obtain before/after evidence — while the existing green/red semantics, portable execution, UAC/worker authentication, centralized-management boundaries and “never weaken security” invariants remain intact.
