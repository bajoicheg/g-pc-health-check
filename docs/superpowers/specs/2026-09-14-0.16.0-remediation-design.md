# 0.16.0 — Remediation allow-list and execution design

## Scope

This sub-spec defines the exact fixed remediation set for 0.16.0, how actions execute, their impact/risk, ordering and preserved security boundaries.

The red **Сделать всё / Do everything** batch means this list — no more and no less. Future actions require a new reviewed descriptor/handler/test; the red button is not an arbitrary repair shell.

## Fixed 0.16.0 action set

The exact `IncludeInDoEverything` set is:

1. `CleanTemp` — delete eligible old ordinary files from the confirmed current session user's Temp using the existing safety boundary.
2. `FlushDns` — flush the Windows DNS resolver cache.
3. `RegisterDns` — request Windows DNS registration for machine interfaces.
4. `DhcpReleaseRenew` — release and renew DHCP leases only on adapters that Windows reports as DHCP-enabled.
5. `WinsockReset` — reset the Winsock catalog; may require reboot.
6. `TcpIpReset` — reset TCP/IP stack configuration using the fixed Windows reset operation; disruptive and may require reboot.
7. `RestartNetworkAdapters` — restart connected physical network adapters selected by fixed runtime criteria; expected to interrupt network/VPN/RDP.
8. `RestartSpooler` — controlled restart of the Print Spooler without deleting queued jobs.
9. `ClearPrintQueue` — controlled Spooler stop, deletion of pending spool files from the fixed Windows spool directory, and restart; intentionally deletes pending print jobs.
10. `RestartUpdateServices` — restart Windows Update (`wuauserv`) and BITS only when the fixed services exist and can be controlled; do not change service startup type.
11. `GpUpdate` — force a Group Policy refresh without forcing reboot/logoff; machine-scoped refresh runs in the administrative path and user-scoped refresh is attempted only in the confirmed original user context.
12. `TimeResync` — request Windows Time rediscovery/resynchronization using the fixed Windows time service command/API.
13. `Dism` — existing `DISM /Online /Cleanup-Image /RestoreHealth`.
14. `Sfc` — existing `SFC /scannow`.

No other action is implicitly included by the words “Do everything”.

## Explicitly prohibited actions

0.16.0 must not contain a handler, registry entry or generic mechanism that:

- disables/stops/uninstalls/weakens Defender, antivirus, EDR/XDR, firewall, VPN security controls, DLP or other protective software;
- creates exclusions for security products;
- changes Windows Firewall rules/profile state;
- clears Windows Event Logs;
- deletes user profiles, saved credentials, browser credentials/history/cookies or arbitrary folders;
- forces a reboot or logoff;
- disables BitLocker or changes disk encryption state;
- installs/removes drivers or software;
- executes caller-supplied PowerShell/CMD/script text;
- executes a caller-supplied arbitrary binary/path;
- controls an arbitrary caller-supplied service or network adapter name.

The application may interact only with the fixed Windows tools/services/resources required by the action implementations below.

## Existing actions

### CleanTemp

Keep the existing implementation and policy intact.

- Host: original GUI/current user process only.
- Admin: no; in fact actual deletion requires a confirmed non-elevated same-user process/session/profile.
- Scope: `%SessionProfile%\AppData\Local\Temp` after existing normalization/containment checks.
- Eligibility: existing age rule, ordinary files only, reparse points excluded.
- Never executed inside the elevated worker.
- If the GUI is already elevated or user/session identity cannot be proven, preflight marks it unavailable rather than cleaning another profile.

### FlushDns

Keep existing fixed `ipconfig /flushdns` semantics. It can remain current-process when used alone; in a larger administrative batch it may execute in the current process after the administrative worker phase. Do not add elevation retry loops.

### DISM / SFC

Keep existing fixed executable paths, arguments, timeouts and captured bounded output. Preserve the order `Dism` before `Sfc` when both are requested.

## New action behavior

### RegisterDns

Use a fixed Windows registration operation such as `%SystemRoot%\System32\ipconfig.exe /registerdns` with bounded timeout/output. No hostname, interface or argument comes from the UI.

Risk: Low/Medium. Verification: later DNS/resource check; success is not proof that DNS infrastructure accepted every registration.

### DhcpReleaseRenew

Operate only on adapters positively identified at runtime as DHCP-enabled. Do not rewrite static IPv4/IPv6 configuration.

Preferred implementation uses fixed Windows networking APIs/WMI per adapter or an equivalent fixed Windows command path whose target set is derived from OS adapter metadata, not user text.

The action records which adapter identities were attempted and separate release/renew results. Failure on one adapter does not fabricate success for another.

Risk: Disruptive. It may drop VPN/RDP/network access.

### WinsockReset

Run the fixed Windows Winsock reset command (`netsh winsock reset` or equivalent fixed API behavior) in the elevated worker. Capture bounded output and mark `MayRequireReboot=true` when Windows reports/semantically requires it.

Risk: High/Disruptive. No automatic reboot follows.

### TcpIpReset

Run the fixed Windows TCP/IP reset operation (`netsh int ip reset` with no caller-controlled target/file) in the elevated worker.

Risk: Disruptive. It may affect custom/static networking and normally requires reboot for full effect. The confirmation must say so before execution; the tool does not force reboot.

### RestartNetworkAdapters

Restart only adapters that satisfy fixed runtime criteria:

- Windows reports the adapter as a physical adapter;
- adapter is currently connected/enabled enough to be a real networking path;
- exclude loopback/tunnel-only/software-only devices by fixed properties, not by user-supplied name patterns;
- record stable adapter identity and friendly name as evidence.

Use a fixed OS API/WMI enable/disable path under elevation. Do not expose arbitrary adapter selection text to the worker protocol for the red batch.

Risk: Disruptive. The action is expected to terminate/re-establish network and may terminate the operator's RDP/VPN session. Re-enable is always attempted in `finally`/cleanup semantics for adapters successfully disabled. Each adapter gets an individual result.

### RestartSpooler

Control only the fixed service name `Spooler`.

- stop with bounded wait if running;
- start with bounded wait;
- do not alter startup type;
- do not delete queue/spool files in this action.

Risk: Medium. Existing print operations may pause; pending jobs are preserved.

### ClearPrintQueue

This is intentionally broader and destructive to pending print jobs:

1. stop fixed service `Spooler` with bounded wait;
2. access only `%SystemRoot%\System32\spool\PRINTERS` after fixed normalized path validation;
3. delete ordinary spool files found directly within that fixed queue location according to the implementation contract; do not follow reparse points and do not recurse outside it;
4. restart Spooler in cleanup/finally even if some files cannot be deleted;
5. report deleted/skipped/error counts and whether Spooler restart succeeded.

Do not inspect or export print-job contents.

Risk: High because pending jobs are intentionally removed.

When `RestartSpooler` and `ClearPrintQueue` are both requested, preflight coalesces the standalone restart as superseded by the queue-clear sequence to avoid two unnecessary stop/start cycles.

### RestartUpdateServices

Only fixed services `wuauserv` and `BITS` are in scope.

- do not change startup mode;
- if a service is running, perform bounded stop/start;
- if stopped/disabled/unavailable, record actual state rather than silently changing configuration; an implementation may start a stopped non-disabled service only if the action contract/test explicitly treats this as the intended repair, but it must never change Disabled to enabled;
- preserve per-service result.

Risk: Medium/High. Existing update/BITS work can be interrupted.

### GpUpdate

No forced logoff/reboot flags.

The action is split by identity:

- machine policy: fixed computer-policy refresh in the elevated path;
- current user policy: attempted only from the original process when process/session identity is confirmed to represent the intended interactive user; never run “user policy” under alternate administrator credentials and label it as the user's result.

Use fixed arguments/options and bounded timeout. If the user-scoped half is unsafe/unavailable, record it as skipped/partial rather than applying policy to the wrong account.

Risk: High. Policy refresh can change workstation behavior/configuration. The app does not claim which GPO caused a later change.

### TimeResync

Use a fixed Windows time resync/rediscover operation under the machine action path. Do not change configured time sources, domain membership or service startup type.

Risk: Low/Medium. Report command/service failure distinctly.

## Execution hosts and UAC

Registry execution-host policy:

- `CleanTemp`: original process only.
- user-scoped portion of `GpUpdate`: original process only when same-user context is confirmed.
- `FlushDns`: original process unless an existing authenticated elevated context is intentionally reused without changing semantics.
- all machine-repair actions requiring administrative rights: one elevated worker.

For a batch that needs elevation:

1. confirmation happens first;
2. current execution context is recaptured and preflight is recomputed;
3. one elevated worker is started through the existing `runas`/UAC path;
4. the worker remains restricted to fixed worker-allowed IDs and existing session/nonce authentication;
5. parent-only actions run only after the elevation path has successfully authenticated/started, so a cancelled UAC produces no surprising pre-UAC modifications;
6. worker/parent results are merged into one batch envelope.

If the GUI is already elevated, machine actions execute without a second UAC, but parent-only same-user actions remain subject to their own safety policy and may be unavailable.

## Worker protocol and allow-list

Do not transmit arbitrary executable names, command arguments, service names, registry paths, spool paths or adapter names supplied by GUI text.

The worker receives only:

- authenticated session/nonce/pipe values under the existing scheme;
- fixed action IDs;
- existing bounded numeric options needed by an approved action (for example Temp age remains parent-only and is not a worker target selector).

The worker maps IDs to compiled handlers. Unknown IDs, mixed allowed+unknown sets and malformed requests are rejected before any action executes.

If registry metadata is used to derive the worker allow-list, add a regression that the derived set matches handler coverage exactly. Do not replace explicit denial with reflection-based “call any matching method”.

## Execution order for the red batch

Default deterministic order:

1. `RestartSpooler` / `ClearPrintQueue` (coalesced as applicable)
2. `RestartUpdateServices`
3. `TimeResync`
4. `GpUpdate` machine portion
5. `Dism`
6. `Sfc`
7. `RegisterDns`
8. `DhcpReleaseRenew`
9. `WinsockReset`
10. `TcpIpReset`
11. `RestartNetworkAdapters`
12. parent/current-user phase: `FlushDns`, confirmed user portion of `GpUpdate`, `CleanTemp`

Rationale:

- long integrity checks complete before intentionally breaking network connectivity;
- network-disruptive operations are grouped late;
- parent user-context operations happen only after UAC success and remain clearly separate from alternate-admin identity;
- CleanTemp never crosses into elevation.

If implementation evidence shows a Windows operation has a stronger ordering dependency, update this order in code/spec/tests before release rather than relying on accidental switch order.

## Timeouts and cancellation

Each handler has a bounded operation timeout appropriate to the Windows component. DISM/SFC keep their existing long bounds. Service/network operations use much shorter bounds.

Once a destructive native operation is issued, “Cancel” cannot pretend to roll it back. Batch cancellation means:

- stop before starting the next action when safe;
- do not kill a Windows operation in a way known to leave state less predictable unless the existing handler already has safe timeout/termination behavior;
- always run required local cleanup such as attempting to restart Spooler or re-enable an adapter that this process disabled;
- report `Partial/Cancelled` with completed action evidence.

No rollback system is added in 0.16.0.

## Reboot semantics

`WinsockReset` and `TcpIpReset` can require reboot, and other Windows tools may recommend one. The batch aggregates a `RebootRecommended/MayBeRequired` result flag and shows it prominently afterwards.

The application never automatically calls shutdown/reboot/logoff in 0.16.0.

## Test-first requirements

No CI test performs these repairs on the GitHub runner. Introduce injectable/native-operation boundaries and synthetic fixtures.

RED/GREEN coverage must include:

- exact 14-action all-set and deterministic order;
- worker allow-list rejects every unknown/prohibited action;
- negative explicit cases such as `DisableDefender`, `StopEDR`, arbitrary service name and arbitrary command text are rejected;
- one worker start for a multi-action admin batch;
- UAC cancellation produces zero parent/worker modifications;
- CleanTemp never enters worker and remains same-user/non-elevated;
- DHCP action never targets static adapters in synthetic inventory;
- adapter restart targets only fixed eligible physical adapters and always attempts re-enable after a simulated failure;
- ClearPrintQueue never escapes the normalized fixed spool directory/reparse boundary and restarts Spooler in cleanup;
- RestartSpooler does not delete queue files;
- Update service action cannot change Disabled startup type;
- GpUpdate user half is not attributed to an alternate-admin identity;
- no action forces reboot/logoff;
- DISM precedes SFC;
- network-disruptive group occurs after DISM/SFC;
- action output is bounded and errors preserve action identity/scope;
- reboot-required aggregation;
- all existing portable EXE, nonce/session, mixed-action denial and security-negative tests remain green.

Managed Windows pilot of the red batch must run only on an approved disposable/test workstation because the intended behavior can interrupt network, VPN/RDP, print jobs and policy/service state.
