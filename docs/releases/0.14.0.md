# 0.14.0 — One selected process on the machine-performance timeline

## Entry and use

Open **Анализ → Подробности процессов…**, collect a current snapshot, select a row with a known nonzero PID and creation time, and choose **Наблюдать за процессом…**. The observation window opens idle; **Начать / повторить** starts a bounded session. There is no action for an event-log emitter PID, no typed arbitrary PID, and no automatic selection of a replacement process.

Defaults are 120 seconds / 2 seconds. Duration choices: 30, 60, 120, 300 or 600 seconds. Interval choices: 1, 2 or 5 seconds. The upper chart shows one selected process metric (CPU, working set, private commit, I/O read or write rate). The lower chart shows one existing machine metric (CPU, physical RAM, aggregate disk busy or queue). Both have the same elapsed-time axis and symptom markers; source receipt timestamps remain separate. Metric selectors do not change collection or export coverage.

**Отметить симптом** records a nonempty note up to 160 characters; at most 100 marks. **Остановить наблюдение** requests cooperative cancellation and retains completed process/system pairs in memory; incomplete pairs are not committed. Stop does not write files. Export before another session or closing: a new session replaces the prior in-memory result. Following process exit, system observation continues until normal completion or stop.

**Сохранить HTML / JSON** creates a unique directory with observation.json and report.html. JSON preserves target, collecting account/context, original native counters, calculated readings, source timestamps, complete machine snapshot, warnings and marks. HTML contains all five process graphs and all four system graphs, statistics, complete pair table and expandable raw JSON. Copy makes a Service Desk summary. Exports contain sensitive process names, paths, accounts/SIDs and notes; review before sharing. Nothing is uploaded automatically.

## Definitions

- One process instance, not the aggregate application/browser/process tree. Initial identity matching uses selected WMI CreationDate precision (microseconds) against native 100-ns FILETIME. The source then keeps one limited-query + synchronize handle; it does not reopen by PID after exit or initial failure. Native creation time is retained.
- Process CPU uses deltas of kernel+user execution time over the actual monotonic interval, divided by the total active logical processors. 100% means all logical processors' capacity, not 100% of that process's affinity, CPU-set, job quota or a single core. Unknown/changed processor counts and invalid deltas yield missing CPU rather than guessed/clamped values.
- Working set includes resident shared pages. PrivateUsage is private committed memory, not physical RAM and not swap-file occupancy. They are different quantities and should not be added.
- Process I/O rates are deltas of Windows-accounted transferred bytes, including I/O beyond physical disk; they are not disk throughput, filesystem latency, or remote transfer speed. Units are MiB/s, with 1 MiB = 1048576 bytes.
- The first sample has memory but no derived CPU/I/O rates. Unavailable samples, decreasing counters, nonpositive intervals and gaps over 1.75 configured intervals break the delta baseline/line. Available zero counters remain zero. CPU above 100% is rejected rather than silently clipped.
- Process sampling precedes the machine read. Each has its own receipt time on the same clock. The existing sequential scheduler does not overlap or burst catch-up reads; slow providers create visible missed slots. No atomic OS snapshot or hard native deadline is claimed. Machine CPU/disk definitions and multi-group limitations remain those of 0.9.0.
- Summary statistics use available samples: min, median, nearest-rank P95, max and count. They are not time-weighted fractions or causal diagnoses. Symptom correlation does not prove the bottleneck. Collection itself affects measured load.

## Safety and unchanged boundaries

Query-only process handle; no memory-content reads, injection, token adjustment, process termination, artificial workload, remote access, new packages or new repairs. Uses existing GUI rights; it does not prompt for elevation. Denied/protected processes stay unavailable. No change to main health/coverage, UAC/worker allow-list, arbitrary portable EXE folder/name, elevated Temp preview, same-user non-elevated Temp deletion, existing application tools or workflow permissions.
