# 0.15.0 — Diagnostic bundle for Service Desk

## What is new

Open **Анализ → Собрать пакет для Service Desk…** to collect a coherent read-only escalation package without opening the individual diagnostic tools one by one. The window opens idle; nothing is collected until **Собрать пакет** is pressed.

Two modes are available:

- **Быстрый** — Health Check + existing assessment/coverage, current process snapshot, local TCP/UDP owner-PID tables, Application/System events from the previous 60 minutes, physical-disk/reliability evidence and execution-context/completeness metadata. It does **not** run a timed performance session or active DNS/TCP probe.
- **Расширенный** — the same point-in-time categories plus an explicit whole-machine performance phase. Default **60 seconds / 2 seconds**; duration 30 or 60 seconds and interval 1/2/5 seconds. Symptom notes entered during that phase are kept on the performance timeline.

Categories are visible before collection with examples of potentially sensitive evidence and may be excluded individually. In Quick mode the performance category is unavailable by design. At least one category is required.

## Collection semantics

The bundle coordinator composes the existing collectors rather than reimplementing their Windows/WMI/Event Log/IP Helper logic. Collection is sequential in 0.15.0 to keep provider interactions and timing interpretable:

1. Health Check + assessment
2. Processes
3. TCP/UDP endpoints
4. Application/System events, last 60 minutes, up to 1000 records per log
5. Storage details
6. Performance only in Extended mode and only when requested

Each source keeps its own state and timestamps. `NotRequested`, `Complete`, `Partial`, `Unavailable` and `Cancelled` are distinct. Failure of one source does not discard evidence already collected from another. A cancelled or partial bundle can still be useful and exportable.

**Collection completeness is not workstation health.** An unavailable source is never converted into a healthy finding. Health Score and Coverage retain their existing meanings and thresholds.

Cancellation is cooperative. Some Windows providers do not support a hard timeout, so pressing Stop may need to wait for the current provider call to return. A new attempt does not erase a previously useful in-memory package unless the new attempt returns useful evidence.

## Output package

Saving is a separate explicit action. Before saving, the UI reminds the operator that evidence may contain accounts/SIDs, process paths and command lines, IP addresses and ports, event messages, device identifiers and symptom notes.

The application always creates a new unique evidence folder first. Optional ZIP creation happens only after folder files are written; a ZIP failure must not delete the evidence folder.

Typical files:

- `summary.html` — triage entry point with existing assessment findings, source-completeness matrix and bounded highlights;
- `manifest.json` — versioned bundle envelope, requested categories and source states;
- `health.json`;
- `processes.json`;
- `endpoints.json`;
- `events.json`;
- `storage.json`;
- `performance.json` and `performance.html` when Extended performance evidence is present.

The summary groups already-collected Critical/Error/Warning events, ranks available process working sets by size, summarizes endpoint counts and storage evidence, and reuses the existing performance-report interpretation. These are evidence summaries, not causal or maliciousness verdicts. A LISTEN socket is not presented as proof of external exposure, a large process is not called bad, and coincident events/performance are not called a cause.

All workstation-provided strings are HTML-encoded in generated HTML. JSON is UTF-8. Output uses unique/CreateNew semantics; older packages are not overwritten.

## Privacy and safety boundaries

There is no automatic upload, cloud enrichment, reputation lookup or generic redaction engine. Search/filtering is not redaction. Review the package before sharing it outside the intended support channel.

Collection runs with the rights of the current GUI process. 0.15.0 does not silently elevate diagnostics and adds no remediation command. The bundle does not invoke:

- the active DNS/TCP resource probe;
- DISM/SFC/DNS-flush or remediation worker actions;
- Temp preview/cleanup;
- file-use investigation;
- process-observation mode;
- service restart, process termination, startup modification, firewall/network reset, driver installation or reboot.

Existing invariants remain: a portable single EXE can run from any valid folder/name; UAC/worker allow-list is unchanged; elevated read-only Temp preview remains allowed; Temp deletion remains verified same-user and non-elevated.

## Validation scope

The implementation is test-first. Behavioral tests cover defaults, opt-outs, source-state/outcome semantics, cancellation, source failure isolation, reports and packaging, UI/privacy controls and safe collector surface. Windows acceptance uses existing safe read-only sources and deterministic synthetic performance evidence; it does not run real remediation or an external network probe.

Hosted Windows Server CI is not a corporate Windows 11 rollout test. Pilot acceptance still includes standard/elevated/alternate-account/RDP sessions, 100/150/200% DPI, VPN/EDR-heavy machines, partial WMI/Event Log access and realistic workstation data volume. Authenticode signing remains absent unless separately introduced and verified.

Exact observed CI/release evidence is recorded in [0.15.0 validation](0.15.0-validation.md).
