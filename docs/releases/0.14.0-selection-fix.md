# Final acceptance found a real selection-order bug

Commit30179106e2b1d2ab9be6ab73e8e6840b3331dd5d, tested merge774d096d74095a285f56669b9db07da170d0395b, Windows EXE34717044867/job103616052090: clean compilation and all previous plus33 behavior/8 integration checks passed; new completion suite7/8. The actual process-view selection regression failed: a known current row did not enable observation.

Root cause: handlers used SelectionChanged while reading CurrentRow/CurrentCell. WinForms raises SelectionChanged before CurrentCellChanged; the first handler can still see the former cell. Both the original process-details update and the new link consequently evaluated old row state. The simpler constructed-link fixture happened to pass because its current cell was already assigned before attaching handlers; the full form test exposed the ordering.

Fix: update details/action availability on CurrentCellChanged in IncidentReviewForm and refresh the new observation link on that same event. Also use it for the new observation sample-detail pane. No authorization rule, native collector, expected assertion or gate is loosened. The actual known/unknown/reselection test remains unchanged and must pass in fresh Windows CI after this patch.

Primary API reference: https://learn.microsoft.com/en-us/dotnet/api/system.windows.forms.datagridview.selectionchanged?view=windowsdesktop-8.0 . Final checked-head, merge and release evidence are recorded in PR #36. Earlier validation notes describe the pre-fix diff; the final parent view now also has this focused event-order correction.
